# TriageIQ model card

Every model in TriageIQ, what it is trained on, how it is evaluated, and where it falls short. All numbers come
from the report files in `backend/reports/` and are reproducible with the scripts named below.

## Data

Real ticket dumps can't be published, so models are trained and evaluated on **synthetic ServiceNow-style data**
for a fictional retailer ("Northwind Retail"), generated by `sample_data/generate_synthetic_tickets.py`:

| File | Purpose |
|---|---|
| `northwind_incidents.csv` (3,000 tickets, seed 42) | Training data |
| `northwind_q3_incidents.csv` (1,500 tickets, seed 7, own ticket numbers) | Unseen data for end-to-end checks through the app |
| `*_ground_truth.csv` | True tower, subcategory, automation status, planted anomalies (never uploaded) |

The generator deliberately adds the mess real dumps have, because without it every model scores ~100% and the
numbers mean nothing:

- the same ticket type ends differently (alerts that defeat auto-remediation, password resets already handled by a
  bot, job failures that turn out to be data bugs)
- 15% vague descriptions ("Not working since morning"), overlapping wording between related types
- 25% wrong or vague category fields, 10% misrouted tickets, 10% useless closure notes
- 3% flipped labels (annotator disagreement), 2.5% planted operational anomalies

**Expect lower scores on real data.** The value of the synthetic set is that it has ground truth.

## 1. Automation status classifier

**Task:** Already Automated / Can Be Automated / Manual Only, for analysing historical tickets.
**Code:** `backend/ml/automation_model.py`, trained by `backend/train_automation_model.py`.

**Model:** XGBoost (multi-class, early-stopped on a validation split) on TF-IDF text features (description +
closure notes) plus priority, channel, team, category field, log resolution time, reassignments, reopens, opening
hour/weekday, bot resolver flag. Isotonic calibration on the validation split.

**Protocol:** stratified 60/20/20 train/validation/test; the test split is scored once.

| Held-out test (600 tickets) | Accuracy | Macro F1 |
|---|---|---|
| Majority class | 46.3% | 0.211 |
| Rule: "resolved by a bot → already automated" | 70.2% | 0.575 |
| Logistic regression, same features | 95.0% | 0.949 |
| **XGBoost, calibrated** | **95.0%** | **0.950** |

- 5-fold CV macro F1: XGBoost 0.962 ± 0.012, logistic regression 0.958 ± 0.008.
- Calibration: expected calibration error 0.028 → 0.012 after isotonic calibration (multi-class Brier 0.087 → 0.088,
  i.e. unchanged).
- Automation score = calibrated P(automatable) × 100. On the test set, tickets in the High tier are 96.3% actually
  automatable, "Not feasible" 4.9%.
- Top SHAP features: bot resolver, resolution time, closure-note terms ("installed", "replaced"), team, category.

**What went wrong and was fixed:** SHAP showed the model using caller names and city names (spurious, and personal
data as features). Names, user handles and site names are now masked before vectorising; extra regularisation
removed the remaining rare-token memorisation.

**Limitations:** logistic regression matches XGBoost here, so the extra complexity buys little on this data.
Almost every ticket gets a confident score, so the Medium/Low tiers are nearly empty on synthetic data. It uses
closure notes, so it is for retrospective analysis, not routing at creation time.

## 2. Category classifier (L1 tower, L2 subcategory)

**Task:** route a ticket when it is opened. **Code:** `backend/ml/category_model.py`, `backend/train_category_model.py`.

**Model:** multinomial logistic regression on TF-IDF word (1-2) and character (3-5) n-grams of the description, plus
channel, category field and priority.

**Creation-time features only.** Closure notes and the assigned team are excluded: they don't exist when a ticket
needs routing, and the team *is* the routing decision. With them the model scored 99-100%, which was leakage.

| Held-out test (600) | L1 tower, 8 classes | L2 subcategory, 16 classes |
|---|---|---|
| Majority class | 27.2% | 13.8% |
| Legacy keyword rules | 35.7% | — |
| The ticket's own category / subcategory field | 70.3% | 76.3% |
| **Logistic regression** | **93.7%** | **92.0%** |

Selective accuracy: when the model's confidence is ≥ 0.9 (83% of tickets for L1, 80% for L2), accuracy is 99.6% and
100%. Those tickets can be routed automatically and the rest sent to a human.

**Main confusions:** AD vs End User and Account unlock vs Password reset (both say "unable to login"), Tablespace vs
Disk space alerts. The legacy rules' "confidence" values were constants written into the code; they have been removed.

## 3. Clustering (ticket themes)

**Code:** `backend/services/cluster_selection.py`, evaluated by `backend/evaluate_clustering.py`.

**Model:** `paraphrase-multilingual-MiniLM-L12-v2` sentence embeddings (384-d), L2-normalised (so KMeans works on
cosine similarity), KMeans with k chosen per upload by silhouette within 10-30 clusters.

| k | Silhouette | ARI vs true subcategory |
|---|---|---|
| 10 | 0.19 | 0.40 |
| 16 | 0.27 | 0.52 |
| 20 | 0.31 | 0.53 |
| 25 | 0.35 | 0.51 |
| 30 | 0.39 | 0.51 |
| HDBSCAN (73 clusters, 4% noise) | — | 0.25 |

**Findings:** silhouette rises monotonically with k on templated ticket text (near-duplicate descriptions reward
ever-smaller clusters), and bootstrap stability is too noisy to choose k either. Agreement with the true categories is
flat for k = 16-30, so k is limited to a range an operations team can act on. Masking hosts and IDs before embedding
was tried and lowered ARI. HDBSCAN fragments the data.

**Limitation:** clusters reflect description wording; ARI ~0.5 means they are useful themes, not a category taxonomy
(the category classifier does that job).

## 4. Anomaly detection

**Code:** `backend/ml/anomaly_model.py`, evaluated by `backend/evaluate_anomaly.py`.

**Model:** IsolationForest (3% flagged) over features measured against each ticket's own type (its L2 subcategory):
resolution time as a robust z-score (median/MAD) within the type, reassignments, reopens, and off-hours activity
weighted by how rare it is for that type.

| Average precision (base rate 2.5%) | Training dump | Unseen dump |
|---|---|---|
| Global resolution-time z-score | 0.16 | 0.26 |
| Previous hand-weighted rule score | 0.27 | 0.32 |
| IsolationForest without type context | 0.77 | 0.73 |
| **IsolationForest with type context** | **0.84** | **0.75** |

At the operating point on the unseen dump: precision 58%, recall 70%. Reassignment storms and off-hours P1s are caught
100%; resolution-time outliers only ~15-40%, because legitimately slow paths of the same ticket type look the same
(adding the predicted automation status to the group did not help consistently).

## 5. Volume forecast

**Code:** `backend/ml/forecast_model.py`.

Candidates: seasonal naive, per-weekday mean of the last 8 weeks, ridge regression on lags 1-14 + weekday, and a small
LSTM (28-day window → next 7 days). Rolling-origin backtest, 8 origins × 7-day horizon.

| Backtest MAE (tickets/day) | Training dump (16.5/day) | Unseen dump (8.2/day) |
|---|---|---|
| Seasonal naive | 5.02 | 3.18 |
| Weekday mean | 3.81 | 2.34 |
| Ridge on lags | 4.03 | 2.45 |
| LSTM | 3.66 | 2.31 |

**Selection rule:** the simplest model within 3% of the best MAE, applied per upload. On the unseen dump the LSTM is
1% better, inside the rule, so the **weekday mean is used**. On the training dump the LSTM's edge is 3.9%, just
outside the rule, so the **LSTM is selected** there, although its RMSE is worse (5.24 vs 5.16); 56 backtest errors
cannot really separate the two. Prediction intervals are the 10th-90th percentiles of the chosen model's backtest
errors, not a formula.

## 6. X-Ray (surrogate explainer)

`backend/services/xgboost_trainer.py` trains an XGBoost per upload on operational features (resolution time,
reassignments, timing, cluster) with the **automation classifier's decisions as labels**. It is a surrogate that
explains the classifier in operational terms; its metrics are **fidelity** (agreement with the classifier), not
accuracy. Before this change it was trained on hand-written pseudo-labels, so its "accuracy" only measured agreement
with those rules.

## End-to-end check through the app

`backend/evaluate_upload.py` scores what the app stored in the database for an upload against ground truth.

Upload of the unseen `northwind_q3_incidents.csv` (1,500 tickets) through the full pipeline:

| What the app stored | Result |
|---|---|
| Automation status (dashboard flags) | 95.6% accuracy, macro F1 0.955 |
| L1 tower | 92.7% |
| L2 subcategory | 89.7% |
| Anomalies flagged by the live endpoint | precision 60%, recall 73% (base rate 2.5%) |
| X-Ray surrogate fidelity to the classifier | 94.3% |
| Tickets confident enough to auto-route (≥ 0.9) | 78% |

Before the classifier, the app's flags scored 66.4% on the same kind of data, and every ticket's automation score was
≥ 50. The LLM classification layer agreed with the classifier on 71% of tickets; its status and solution lever are now
aligned to the classifier so every tab shows the same answer.

## Measuring accuracy on a new customer (Review Queue)

Test scores above come from the Northwind test set; on a new customer's dump accuracy is unknown until it is
measured. The Review Queue (`backend/routers/review.py`) lets analysts label tickets:

- **Random sample mode** serves tickets in a fixed shuffled order per dataset. Only these labels measure accuracy,
  reported with a 95% Wilson confidence interval once at least 30 are labelled.
- **Least confident first** serves the tickets the classifier is least sure about (daily triage). These labels are
  excluded from the accuracy estimate because the queue deliberately picks hard tickets.
- The model's own prediction is stored separately (`model_status`) from the analyst's label (`human_override`), so
  labels can override the dashboard without losing the ability to measure the model.
- Every label is also training data for the next retraining. Once the active model has been retrained on analyst
  labels, the accuracy estimate only counts labels it never saw: the frozen gold set (below) and labels made after
  its training run. On the Contoso upload that leaves 46 of 300 labels (100%, 95% CI 92.3-100%, against a true 92.6%
  on the unlabelled tickets); counting all 300 gave an inflated 97%.

Check of the method on the Northwind Q3 upload: 60 randomly sampled labels measured 91.7% (95% CI 81.9-96.4%);
the true accuracy over all 1,500 tickets is 95.6%, inside the interval.

## Learning loop: retraining from analyst labels

`backend/services/model_lifecycle.py`, triggered from Model Health (admin) or the API.

1. Training pool = base labelled data + every analyst label from the Review Queue.
2. **Frozen gold test set**, never trained on: the base data's 20% held-out split plus 1 in 5 random-sample analyst
   labels, chosen by a hash of the ticket id so the selection never changes.
3. **Evaluation gate:** the candidate is promoted only if macro F1 on the gold set improves by ≥ 0.005 overall (or
   ≥ 0.01 on the analyst part) **and** it is not worse by more than 0.01 on the base part. Otherwise it is stored
   as "rejected" with the reason.
4. Every run is logged in **MLflow** (parameters, gold metrics for candidate and active model, the decision, the
   model file); every model file is versioned and any version can be re-activated (rollback).

**Drift** (`backend/services/drift.py`) runs on every scored upload against a snapshot of the training data stored
in the model: PSI of resolution time / reassignments / opening hour, vocabulary coverage relative to the training
text's own coverage, share of unseen teams / categories / channels, and the unsure-ticket rate.

**Experiment** (`backend/experiments/learning_loop.py`): a second synthetic customer ("Contoso": same work, its own
team names, service accounts and wording), uploaded through the app.

| Step | Result |
|---|---|
| Active model on Contoso | 73.1% accuracy; drift *significant* (all teams unseen, 58% known words); "Already Automated" recall 0.7% because Contoso's bot accounts have different names |
| Review Queue estimate from 300 random labels | 74.7% (95% CI 69.5-79.3%), consistent with the true 73.1% |
| Retraining | promoted: macro F1 +0.029 on the gold set, +0.42 on Contoso's gold labels (46 tickets), +0.006 on the base gold set |
| Re-scored Contoso, 2,200 tickets nobody labelled | **92.6%**; "Already Automated" recall 88%; drift *stable* |

Two lessons: the model was **confidently wrong** on Contoso (only 1% of tickets below 0.6 confidence), so
confidence alone cannot detect a new customer; drift monitoring did. And a retraining run with no new labels was
correctly **rejected** (+0.002 macro F1, within noise).

On a real customer dump (37,809 tickets, not included in this repository) the current model knows 22% of the words
(60% on its training text) and 84% of teams are unseen: drift *significant*, so its predictions there need a
labelled sample before use.

## 7. Copilot (retrieval-augmented question answering)

**Code:** `backend/services/rag/` (`retrieval.py`, `tools.py`, `answer.py`), `backend/routers/rag.py`,
evaluation `backend/experiments/rag_eval.py`.

**How a question is answered**
1. *Plan.* The local LLM (Qwen 2.5 7B on Ollama) returns JSON constrained by a schema: a data-tool call, a ticket
   search phrase, both, or neither. The prompt maps service-desk terms (MTTR, TAT, volume, SLA breach) to metrics.
   An invalid plan is sent back with the validation error once (self-repair).
2. *Entity linking.* Teams, channels, resolvers and priorities named in the question are matched against this
   dataset's values in code, and added as filters if the planner left them out.
3. *Numbers* come from a whitelisted aggregate tool (4 metrics × 8 dimensions, validated by pydantic, built with
   SQLAlchemy and bound parameters). Model output never becomes SQL text. A filtered average or rate also returns
   the unfiltered figure for comparison. Grouped results also carry each group's average resolution time.
4. *Explanations* come from hybrid retrieval over description + closure notes: MiniLM embeddings (exact cosine) and
   Postgres full-text search, merged with reciprocal rank fusion (k = 60).
5. *Answer* uses only that evidence; ticket text is passed as quoted data, not instructions.
6. *Verify.* Citations to tickets that were not retrieved are removed. Numbers that appear in neither the evidence
   nor the question are flagged; if any are found, the answer is regenerated once and checked again. If the second
   answer still fails, it is withheld (fail closed) and only the data table is shown.

**Evaluation** (Northwind Q3, 1,500 tickets, answer key from the generator; 3 runs of v1, then 3 + 1 runs after
the fixes below)

| | Copilot | Previous copilot (SQL summaries in the prompt) |
|---|---|---|
| Numeric questions correct (15) | 100% (93.3% in 3 runs with a flawed test item, see below) | 53% |
| Out-of-scope questions declined (5) | 100% | 80–100% |
| Answers citing a ticket that was not retrieved | 0% | n/a (no citations) |
| Answers with a number not in the evidence, first draft | 0–14% | not checked |
| …after the correction pass | 0% | |
| Latency p50 / p95 | 5.8–6.1 s / 10.3–13.3 s | |

Retrieval, 16 questions phrased differently from the ticket text (one per true subcategory), precision@8 / hit@1:

| Vector | Keyword | Hybrid |
|---|---|---|
| 0.906 / 0.812 | 0.867 / 0.812 | **0.953 / 0.938** |

**A failure found in use.** Asked just "MTTR", v1 answered 22.62 h: the planner returned every filter as
`null`, validation rejected the plan, the system fell back to ticket search, and the model averaged 7 sample
tickets. The checker flagged the numbers but the answer was still shown. Fixes: null filters are dropped,
service-desk terms are in the planner prompt, invalid plans get one repair attempt, team/priority names are linked
in code, and answers that still fail verification are withheld. Three regression questions were added ("MTTR", "TAT
for P1", "the team with most tickets and its MTTR"). A resolver version of the last question was removed because
two resolvers tie at 133 tickets, so it had no single correct answer; that item caused the 93.3% runs.

**Limitations**
- The question set is small (36 questions) and was written by the system's author. One failure (the planner dropped a
  team filter) was fixed after it was seen; two further filtered questions were added afterwards and pass, but this
  is not a blind test.
- The number check catches numbers that are absent from the evidence, not a real number attached to the wrong thing.
- Each question is answered independently; there is no conversation memory.
- Indexing a 37,809-ticket customer dump took 284 s on CPU. Exact search over 1M tickets is ~1.5 GB of vectors.

**Vector store** (`experiments/vector_store_benchmark.py`, 300 queries, k = 8). Two implementations sit behind one
interface: exact search over a numpy matrix, and pgvector with an HNSW index (used in Docker).

| Dataset | Recall@8 | Tie-aware recall@8 | Exact search p50 | pgvector HNSW p50 / p95 |
|---|---|---|---|---|
| Northwind Q3, 1,500 tickets | 98.8% | 100% | 0.24 ms | 4.4 / 6.6 ms |
| Contoso, 2,500 tickets | 97.4% | 100% | 0.32 ms | 5.4 / 8.4 ms |

Every HNSW "miss" was a tie: templated tickets have identical vectors, and HNSW returned a different ticket with the
same similarity. At this size exact in-process search is ~18x faster than a database round trip; pgvector is chosen
for shared storage across API workers and for the 1M-ticket scale test, where the comparison has to be repeated.

## What is not a model

- **SLA analysis:** share of the SLA target each resolved ticket used (resolution time ÷ target for its priority).
  Descriptive, not a prediction. A breach predictor at creation time is future work.
- **Savings:** analyst effort removed per automated ticket (15 min) × ₹850/hour, averaged over the months the dump
  covers. Both assumptions are shown next to every figure.
